# 前端发版后如何优雅地提醒用户刷新页面

> **作者**：gouxinjie
> **日期**：2026-08-03
> **技术栈**：Next.js 14 · React 18 · TypeScript · Nginx · Docker
> **源码**：https://github.com/gouxinjie/mylab

## 一、问题背景

前端应用（尤其是 SPA 或依赖长缓存资源的站点）发版后，**已经在浏览器中打开旧页面的用户**往往不会立即看到新版本。他们的标签页可能已经挂了很久，加载的是旧 JS/CSS 资源，直到手动刷新才会更新。

对于动态内容频繁更新的站点，这会导致用户看到"过期"的界面，甚至出现新旧接口不一致导致的报错。最朴素也最可靠的做法，就是**发版后提醒用户刷新页面**。

常见的实现思路有几种，本文先做对比，再给出一种在真实项目（Next.js + Docker + Nginx 部署）中落地、并经受住了线上踩坑的方案。

## 二、方案对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **静态版本文件 + 轮询** | 构建时生成 `version.json`，前端定时拉取对比 | 简单可靠，无后端依赖 | 有轮询延迟 |
| 构建号注入 `window` | 构建期把版本号写进 HTML/全局变量 | 无额外请求 | 旧页面拿不到新值，仍需轮询或对比 |
| SSE / WebSocket 推送 | 服务端主动推送版本变更事件 | 实时 | 需常驻连接，方案较重 |

对于大多数纯前端项目，**方案一（静态版本文件 + 定时轮询）** 是性价比最高的选择：实现简单、不依赖后端、可部署在任何静态服务或 CDN 之后。

## 三、核心设计

整体思路拆成三步：

1. **构建时生成版本标识**：每次 `build` 时，把当前构建时间写入 `public/version.json`。
2. **前端轮询对比**：客户端定时拉取 `version.json`，与"基准版本"对比，不一致则说明发生了发版。
3. **提示刷新**：检测到发版后，弹出提示让用户点击刷新（不自动消失）。

### 3.1 关键点：基准版本从哪里来？

这是最容易出错的地方。很多初版实现会用 `localStorage` 或页面加载时的当前时间作为基准，这会导致两个问题：

- **首屏误报**：基准与真实构建版本不一致，用户刚打开页面就误弹"已更新"。
- **无法跨会话检测**：用户昨天访问过、今天再来，如果基准只在本次会话内存着，就检测不到"今天又发了版"。

正确的做法是**双重基准**：

- **首次访问**（localStorage 无记录）：以服务端 `version.json` 的 `buildTime` 为基准，避免首屏误报。
- **再次访问**（localStorage 有记录）：以 localStorage 中"上次访问时的 buildTime"为基准，与当前服务端对比，实现跨会话检测。

这样既覆盖"用户一直挂着旧标签页"的场景（靠轮询），也覆盖"用户隔几天再次打开"的场景（靠 localStorage 对比）。

## 四、具体实现

### 4.1 构建时生成版本文件

新建 `scripts/generate-version.mjs`：

```js
/**
 * 生成前端版本标识文件
 * 在每次 build / start 前执行，将构建时间戳写入 public/version.json。
 * 前端定时拉取该文件，对比 buildTime 判断是否发生发版。
 */
import { writeFileSync, mkdirSync } from "node:fs";
import path from "node:path";

const publicDir = path.resolve(process.cwd(), "public");
const target = path.join(publicDir, "version.json");

mkdirSync(publicDir, { recursive: true });

const version = {
  version: new Date().toISOString(),
  buildTime: Date.now(),
};

writeFileSync(target, JSON.stringify(version, null, 2), "utf-8");
console.log(`[version] 已生成 ${target} -> ${version.version}`);
```

在 `package.json` 的 `build` / `start` 前注入执行：

```json
"build": "node scripts/generate-version.mjs && next build",
"start": "node scripts/generate-version.mjs && next start --port 3500",
"dev": "node scripts/generate-version.mjs && next dev --port 3500"
```

> 注意：`dev` 也要加上，否则本地开发时 `version.json` 不存在，前端会一直请求 404。

### 4.2 前端检测组件

新建 `components/commons/VersionCheck/index.tsx`：

```tsx
/**
 * @component VersionCheck
 * @description 发版检测组件：定时拉取 version.json，若构建版本变化则通过 toast 提示用户刷新页面。
 * @author gouxinjie
 */
"use client";

import { useEffect, useRef } from "react";
import toast from "react-hot-toast";

/** 轮询间隔（毫秒），默认 1 小时 */
const POLL_INTERVAL = 3_600_000;
/** 请求禁用缓存，确保每次拿到最新版本 */
const FETCH_INIT: RequestInit = { cache: "no-cache" };
/** localStorage key：持久化最近一次已知 buildTime，支持跨会话检测 */
const STORAGE_KEY = "__APP_BUILD_TIME__";

interface VersionInfo {
  version: string;
  buildTime: number;
}

/** 拉取最新版本号 */
const fetchLatestBuildTime = async (): Promise<number | null> => {
  try {
    const res = await fetch("/version.json", FETCH_INIT);
    if (!res.ok) return null;
    const data = (await res.json()) as VersionInfo;
    return typeof data.buildTime === "number" ? data.buildTime : null;
  } catch {
    return null; // 网络异常静默失败，下次轮询再试
  }
};

const renderUpdateToast = (): React.ReactElement => (
  <span>
    站点已更新，请
    <button type="button" onClick={() => window.location.reload()}>
      刷新页面
    </button>
    以获取最新内容。
  </span>
);

export default function VersionCheck() {
  const buildTimeRef = useRef<number>(0);
  const notifiedRef = useRef<boolean>(false);

  useEffect(() => {
    // 初始化：读 localStorage 旧基准 + 拉取服务端版本
    const init = async () => {
      const stored = Number(localStorage.getItem(STORAGE_KEY));
      const storedValid = Number.isFinite(stored) && stored > 0;
      if (storedValid) buildTimeRef.current = stored;

      const latest = await fetchLatestBuildTime();
      if (latest === null) return;

      if (!storedValid) buildTimeRef.current = latest; // 首访以远端为准，避免误报
      localStorage.setItem(STORAGE_KEY, String(latest));

      if (storedValid && stored !== latest) {
        // 跨会话发版检测：本地旧版本 != 远端，立即提示
        notifiedRef.current = true;
        toast(renderUpdateToast(), { id: "version-update", duration: Infinity });
      }
    };

    void init();

    const timer = setInterval(async () => {
      if (buildTimeRef.current === 0) return;
      const latest = await fetchLatestBuildTime();
      if (latest !== null && latest !== buildTimeRef.current && !notifiedRef.current) {
        notifiedRef.current = true;
        localStorage.setItem(STORAGE_KEY, String(latest));
        toast(renderUpdateToast(), { id: "version-update", duration: Infinity });
      }
    }, POLL_INTERVAL);

    return () => clearInterval(timer);
  }, []);

  return null;
}
```

### 4.3 挂载到全局布局

在根布局 `<body>` 内、全局 `Toaster` 之后挂载：

```tsx
<Toaster position="top-center" />
<VersionCheck />
```

## 五、两个必须避开的坑

这套方案我在真实项目里踩过两个坑，单独拎出来讲。

### 坑一：next-intl 中间件把 version.json 重写成了 /zh/version.json

这是最隐蔽、也最致命的问题。项目用了 `next-intl` 做国际化，路径前缀策略为 `localePrefix: "always"`（中文 `/zh`、英文 `/en`）。其 `middleware.ts` 的 matcher 大致长这样：

```ts
export const config = {
  matcher: [
    "/((?!_next|images|logos|data|imgs|favicon.ico|api|health|.*\\.png|.*\\.svg|.*\\.ico|.*\\.woff2).*)",
  ],
};
```

当浏览器请求 `/version.json` 时，因为它**不在排除列表、也不以图片/字体后缀结尾**，被 next-intl 中间件当成了"需要加 locale 前缀的页面路由"，**重写成了 `/zh/version.json`**。而 `/zh/version.json` 不是有效页面，返回 **404**，导致前端永远拿不到版本信息。

浏览器控制台会看到这样的报错：

```
GET http://gouxinjie.com/zh/version.json 404 (Not Found)
```

**修复**：在中间件 matcher 排除列表中加入 `version.json`（以及更稳妥的 `.*\.json`）：

```ts
matcher: [
  "/((?!_next|images|logos|data|imgs|favicon.ico|api|health|version.json|.*\\.json|.*\\.png|.*\\.svg|.*\\.ico|.*\\.woff2).*)",
],
```

同时，`next.config.js` 中 `headers()` 的正则也建议把 `version.json` 排除，避免它被套上不必要的响应头。

### 坑二：Docker 构建缓存导致 version.json 不更新

生产通过 CI 的 `docker build`（带 gha 缓存）构建镜像，`public/version.json` 在 `RUN pnpm run build` 阶段生成，随后 `COPY` 进运行镜像。如果发版时源码未变（比如只改了运行配置），`RUN` 层缓存可能命中，镜像里的 `version.json` 就不会更新。

**规避**：每次真正发版必然伴随代码变更，`COPY . .` 层内容会变化，从而打破缓存。若遇到"改了但版本没更新"的情况，可检查 CI 是否需要强制无缓存构建，或在生成脚本里额外写入一个每次必变的字段。

### 坑三：Nginx 层禁用缓存

`version.json` 必须**禁止任何缓存**，否则前端即使轮询，拿到的也是浏览器/CDN 缓存的旧文件，永远对比不出差异。在 Nginx 中为它单独加一条规则：

```nginx
location = /version.json {
    add_header Cache-Control "no-store" always;
    proxy_pass http://app:3500;
}
```

同时前端请求要带 `cache: "no-cache"`，双保险。

## 六、验证与测试

由于检测机制的基准来自"页面加载那一刻的版本"，**"没发版就不弹"是必然的**。要验证弹窗，需要主动制造一次版本变化：

1. 部署新代码后，正常打开一次站点（会写入 localStorage 基准）。
2. 手动修改生产环境的 `public/version.json`，把 `buildTime` 改成不同的值（或直接等下一次真实发版）。
3. 刷新页面 → 立即弹出"站点已更新，请刷新页面"；或保持旧标签页打开，最多等一个轮询周期也会弹出。

## 七、总结

| 环节 | 要点 |
|------|------|
| 版本来源 | 构建时生成 `version.json`，以 `buildTime` 作为唯一版本标识 |
| 基准策略 | 首访以远端为准，再访以 localStorage 旧值对比，双重覆盖轮询与会话 |
| 请求缓存 | 前端 `cache: "no-cache"` + Nginx `no-store`，杜绝缓存污染 |
| 国际化 | 必须把 `version.json` 加入 next-intl 中间件排除列表 |
| 提示方式 | toast 弹窗，不自动消失，用户点击刷新 |

这套方案没有引入任何额外后端依赖，纯粹利用静态文件 + 定时轮询，即可在纯前端站点上实现"发版后提醒刷新"，并且能覆盖"标签页长期挂载"和"跨会话再次访问"两种最常见的真实场景。
